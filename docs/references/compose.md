# Compose API

Compose 接口用于单机 Docker Compose 与 Swarm Stack 的部署、读取配置、重部署，以及按服务更新镜像并重建。Docker Compose 读取与重部署支持按 `com.docker.compose.project` 标签聚合外部 `docker compose up` 启动的既有项目。

Docker 不可用时 `/compose/*` 返回 `503`；未配置 `docker.containerRoot` 时部署、读取配置和历史接口返回 `500`「未配置容器数据根目录」。

## Webview 部署入口

桌面和移动端共用「Compose 部署」导航，包含「单机容器」「Swarm 服务」和「应用市场」。

- 「单机容器」位于 `/compose/docker`，需 Docker 能力有效且有 `POST /api/compose/docker` 权限。
- Swarm 服务：`/compose/swarm`，需 Swarm 管理节点能力有效且有 `POST /api/compose/swarm` 权限。
- 「应用市场」位于 `/compose/marketplace`，至少一种部署目标可用时显示。选择模板后优先进入「单机容器」，仅 Swarm 可用时进入「Swarm 服务」。

部署入口同时要求 Compose 能力有效；两种目标均不可用时隐藏整个「Compose 部署」菜单，单个目标不可用时隐藏对应子菜单。两条部署路由复用同一表单组件，由路由固定目标，不再使用 `target` 查询参数；旧 `/compose/deploy` 链接需更新。清空表单不改变当前部署目标。

## 字段说明

### 部署请求

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `content` | string | 是 | 完整 compose yaml 文本，顶层必须有非空 `name` |
| `envContent` | string | 否 | `.env` 内容（`KEY=VALUE`）；省略则保留附加文件解压出的 `.env`（不存在时兜底创建空 `.env`，避免 `env_file` 因缺文件报错），提交则以其为准写盘并合并进变量插值环境 |
| `initURL` | string | 否 | 附加运行文件 ZIP 下载地址，下载最多等待 5 分钟 |
| `initFile` | file | 否 | 附加运行文件 zip（仅 multipart）；与 `initURL` 同时提交不会报错，此时只使用 `initFile`，`initURL` 被忽略 |
| `forcePull` | boolean | 否 | 单机 Docker 设为 `true` 时强制拉取最新镜像，默认 `false`，仅 JSON 请求生效。Swarm 首次部署总会查询镜像摘要，此字段对其无影响 |

> Docker 与 Swarm Compose 部署都支持 `initURL` / `initFile`；解压目标为 `docker.containerRoot/<NAME>/`。Swarm 场景下建议 `containerRoot` 指向各节点共享的存储（如 NFS），以便所有节点都能访问解压出的文件。

`.env` 提交约定：省略 `envContent` 保留附加文件或现有 `.env`；提交精确内容则覆盖；提交空字符串则清空。

Docker 和 Swarm 的部署、重部署均保留现有 `.env` 的权限，Unix 系统上也保留所有者和所属组。新建 `.env` 使用 `0644`，实际权限受 iSrvd 进程的 `umask` 限制。

新建和重部署均要求 Compose 顶层显式提供非空 `name`，不接受缺失、`null`、空字符串或纯空白。项目名按 compose-go 规则插值并规范化；插值结果为空时拒绝。重部署时项目名必须与当前项目一致。

部署前的冲突校验（任一命中即报错）：

- 安装目录已存在 compose 配置：`目录 <DIR> 已包含 compose 配置，请先移除`
- Docker：同名容器已存在：`容器名称 <NAME> 已被占用`
- Swarm：同名服务已存在：`服务 <NAME> 已存在，请先移除`
- compose 中未定义任何服务：`compose 文件中没有定义服务`

附加 ZIP 的归档大小和解压总量分别限制为 512 MiB。附加文件与现有文件重名时拒绝部署，`compose.yml` 由请求中的 Compose 配置生成。请求取消会中止附加文件下载和解压。部署失败时清理本次新建的文件与空目录，并恢复原 `.env`。

Docker 和 Swarm 仅检查启用服务实际引用的网络及具名 `network_mode`；这些引用中的 `external: true` 网络必须已存在。未使用或仅禁用 profile 引用的顶层网络不检查、不创建。部署失败后尝试清理本次确认新建的网络，网络仍有连接或清理失败时报告错误。

状态码：`400` 为 JSON/表单解析失败、`content` 为空、请求体超过 `server.maxUploadSize`、路径参数 `:name` 非法；其余错误（含项目名非法、冲突校验、重部署参数校验、部署忙碌）返回 `500`。

### 重部署请求

Docker 配置中的 `volumes: [/data]` 会创建匿名卷。重部署同一服务时，如果相同挂载目标仍声明为匿名卷，则复用能确认归属的旧匿名卷。改用命名卷或绑定目录时，按新挂载配置执行。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `content` | string | 按需 | 完整 compose yaml 文本；省略表示沿用现有 compose.yml，提交空字符串会被拒绝；最终配置必须包含与当前项目一致的 `name` |
| `envContent` | string | 按需 | `.env` 内容（`KEY=VALUE`）；省略表示保留现有 `.env`（不存在时兜底创建空 `.env`），提交空字符串表示清空，提交内容表示覆盖 |
| `serviceName` | string | 按需 | 要更新镜像的 compose 服务名（按服务更新） |
| `image` | string | 按需 | 新镜像名，`serviceName` 非空时必填 |
| `forcePull` | boolean | 否 | 默认 `false`。设为 `true` 时，单机 Docker 强制拉取最新镜像，Swarm 重新解析镜像标签，摘要变化可触发滚动更新 |

> 部分更新：未提交的字段保持不变；`content`、`envContent`、`serviceName` 至少提交一项；`serviceName` 与 `content`、`envContent` 互斥，`serviceName` 非空时 `image` 必填。

重部署前的配置保存在版本快照中。Docker 重部署失败时尝试恢复原有的 `compose.yml`、`.env` 以及本次已移除的容器。容器使用原镜像 ID 和启停状态重建，复用已有挂载卷。回滚结果在错误摘要中逐项报告。容器 ID 和可写层会随重建变化。此前由运行态生成配置的项目仍可恢复至没有 `compose.yml` 的状态。Swarm 重部署时对已有服务原地更新，对新增服务创建；失败时尽力恢复已更新的服务并移除新建服务，同时恢复旧配置和 `.env`。配置回滚摘要分别列出 `compose.yml` 与 `.env` 的恢复结果；配置写入阶段失败时，摘要只列出文件恢复结果。Swarm 回滚复用上一版服务规格及其镜像引用，不重新解析镜像标签。Swarm 不提供跨多个服务的原子事务，回滚失败会在错误中返回；已删除的服务需重建，ID 可能变化。预检用本次提交的 `.env` 解析配置，执行前写入文件，并复用预检完成的项目。按服务更新镜像时，compose.yml 经 compose-go 加载后整体重新序列化（带 `# Auto-generated by iSrvd` 文件头）：原有注释与格式会丢失，`${VAR}` 会被替换为当时的实际值。

读取 Compose 配置或 `.env` 时若落盘文件存在但读取失败（权限/IO），接口直接报错，不会把读取失败当作「无文件」。

### 部署记录与历史配置

每个 Docker/Swarm 项目最多保留最近 10 条记录（新到旧），同时按约 1 MiB 的加密记录预算移除最旧记录；单个快照的 JSON 明文不能超过 512 KiB。新建成功后记录 `deploy`；重部署在预检通过后先保存 `snapshot`（与最近记录配置一致时复用已有快照），再记录 `redeploy` 的成功或失败。预检失败和新建失败不记录。失败记录不包含配置快照或原始错误。记录只表示部署调用完成，不代表应用已通过健康验收；成功后快照读取失败或超限时仍保存无快照的成功记录。

```bash
isrvd_get "/compose/docker/<NAME>/history"
isrvd_get "/compose/swarm/<NAME>/history"
```

列表只返回以下只读字段，不返回配置内容：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 记录 ID |
| `time` | string | RFC3339 记录时间 |
| `action` | string | `snapshot`（变更前配置）、`deploy`、`redeploy` |
| `success` | boolean | 是否成功 |
| `hasSnapshot` | boolean | 是否可以读取配置快照 |

通过配置读取接口的 `revision` 参数获取快照，响应为配置详情；指定 `revision` 时优先于 `force`。读取快照沿用配置读取权限，记录列表需要相应 history 路由权限：

```bash
isrvd_get "/compose/docker/<NAME>?revision=<ID>"
isrvd_get "/compose/swarm/<NAME>?revision=<ID>"
```

API 恢复配置时，先读取快照，再通过重部署接口提交两个字段（空 `.env` 也必须显式提交）：

```bash
isrvd_put "/compose/docker/<NAME>" '{"content":"<HISTORICAL_COMPOSE_YAML>","envContent":"<HISTORICAL_ENV_OR_EMPTY>"}'
isrvd_put "/compose/swarm/<NAME>" '{"content":"<HISTORICAL_COMPOSE_YAML>","envContent":"<HISTORICAL_ENV_OR_EMPTY>"}'
```

存储与安全：

- 快照整体 AES-GCM 加密，密钥由 `server.dataSecret` 派生。旧安装首次升级时沿用原 JWT 密钥的加密材料，无须重写历史快照；之后 JWT 轮换不会影响快照。需随配置备份 `dataSecret`，不得手工更改。
- 每份快照保存在 `docker.containerRoot/<PROJECT>/compose.<目标>-<记录ID>` 文件（含加密快照与元数据的 YAML，非可运行的 Compose 配置）；`.isrvd-history-docker.yml`、`.isrvd-history-swarm.yml` 仅保存轻量记录索引。即使系统配置使用 etcd，这些文件也写入项目本地目录（Swarm 为管理节点或共享存储），备份时随项目目录一起备份。
- 项目目录、索引和版本文件不能为符号链接；写入使用原子替换，新文件权限 `0600`。
- 索引提交成功后清理被淘汰和未被引用的版本文件；索引提交失败则移除本次新建的版本文件。
- 单个版本文件缺失、损坏或记录不匹配时，该记录降级为无快照，读取该版本返回错误；索引自身读取失败返回错误。
- 索引缺失时，从系统配置存储中的 `compose-<目标与项目名的 SHA256>.yml` 导入旧记录（支持本地文件与 etcd）；导入或快照拆分失败返回错误。
- 重部署前读取当前配置并保存快照，任一步骤失败均在删除实例前返回错误；部署完成后的记录写入失败只记日志。同一 isrvd 实例同时只执行一个 Compose 部署，忙碌时新请求立即返回错误。

历史配置恢复只覆盖 Compose 文本和 `.env`（原先不存在的 `.env` 会变为空文件），不恢复数据库、数据卷、附加文件、外部 `env_file` 或进程环境；未固定 digest 的镜像 tag 不能保证还原旧镜像。

### 变量插值优先级

进程环境优先于项目 `.env`。省略 `envContent` 时使用磁盘 `.env`，提交时以请求内容作为完整 `.env`，空字符串表示清空。预览时，变量插值与指向项目 `.env` 的 `env_file` 引用均使用提交的内容，磁盘文件保留原样。

### 部署结果

| 字段 | 类型 | 说明 |
|---|---|---|
| `projectName` | string | 实际使用的项目名 |
| `items` | string[] | 创建或重建的容器/服务，格式 `<name> (<12 位短 ID>)` |
| `installDir` | string | 项目落盘目录（Docker Compose 与 Swarm 均返回） |

### 配置详情

| 字段 | 类型 | 说明 |
|---|---|---|
| `content` | string | compose.yml 文本 |
| `envContent` | string | `.env` 文本（`KEY=VALUE`）；无落盘文件或内容为空时不返回 |
| `projectName` | string | 实际解析到的项目名 |
| `fileModTime` | number | `docker.containerRoot/<PROJECT>/compose.yml` 修改时间（Unix 秒）；无落盘文件时不返回 |
| `source` | string | 内容来源：`file` 表示落盘文件，`runtime` 表示从运行态反推 |

## Docker Compose

### 部署

Docker Compose 部署支持 JSON；上传附加运行文件时使用 multipart form。

部署请求总大小受 `server.maxUploadSize` 限制。

仅提交 compose 内容：

```bash
isrvd_post "/compose/docker" "$(jq -n --arg content "$(cat docker-compose.yml)" '{content:$content}')"
```

上传本地附加文件：

```bash
isrvd_upload "/compose/docker" "initFile" "./init.zip" "content=$(cat docker-compose.yml)"
```

使用远程附加文件：

```bash
isrvd_post "/compose/docker" '{"content":"<COMPOSE_YAML>","initURL":"<HTTPS_ZIP_URL>"}'
```

> `initURL` 由后端直接发起 HTTP GET 下载（仅 `http/https` 可用），**当前未校验目标是否为本机/内网/链路本地地址，也不限制重定向**；请仅使用可信地址。

### 读取 compose 文件

```bash
isrvd_get "/compose/docker/<NAME>"
```

`<NAME>` 可以是 iSrvd 项目名，也可以是带 `com.docker.compose.project` 标签的容器名。读取顺序：

1. 优先读取 `docker.containerRoot/<PROJECT>/compose.yml`，响应中的 `fileModTime` 为该文件修改时间
2. 文件不存在时，按 `com.docker.compose.project=<PROJECT>` 聚合同项目容器并反推多服务 compose
3. 无 compose project 标签时，退回单容器 inspect 反推

强制从运行态反推（跳过已有 `compose.yml`，但仍返回已有文件的 `fileModTime`）：

```bash
isrvd_get "/compose/docker/<NAME>?force=true"
```

Docker Compose 中的相对 bind path 会基于容器目录 `docker.containerRoot/<PROJECT>` 解析，部署、全量重部署、按服务更新镜像和失败回滚保持一致。后端统一使用 compose-go loader 解析与标准化 YAML，再直接生成 Docker SDK `container.Config` / `container.HostConfig`（Docker）或 `swarm.ServiceSpec`（Swarm）原始结构，不经过 iSrvd 自定义中间 DTO。

- **Docker 支持字段**：`entrypoint`、`command`、`dns`、`dns_opt`、`dns_search`、`extra_hosts`、`tty`、`stdin_open`、`read_only`、`stop_signal`、`sysctls`、`device_cgroup_rules`、`devices`、`security_opt`、`group_add`、`ipc`、`pid`、`uts`、`cgroup`、`runtime`、`shm_size`、`tmpfs`、`ulimits`、`cap_add`、`cap_drop` 等；`deploy.resources` 仅支持 `limits.memory`、`limits.cpus`（`mem_limit` / `cpus` 兜底）与 `reservations.devices`，`reservations.memory` / `reservations.cpus` / `limits.pids` 会被忽略
- **Swarm 支持字段**：`environment`、`entrypoint` / `command`、`working_dir`、`user`、`hostname`、`extra_hosts`、`tty`、`stdin_open`、`read_only`、`stop_signal`、`sysctls`、`cap_add` / `cap_drop`、`dns` / `dns_opt` / `dns_search`、`deploy.mode` / `replicas`、`networks`（含 `aliases`）、`ports`、`volumes`、`deploy.placement.constraints` / `preferences` / `max_replicas_per_node`、`healthcheck`、`logging`、`group_add`、`init`、`stop_grace_period`、`ulimits`、`deploy.endpoint_mode`、`deploy.labels`、`deploy.restart_policy`、`deploy.update_config`、`deploy.rollback_config`、`deploy.resources`（`limits.memory` / `cpus` / `pids`，`reservations.memory` / `cpus`）；`devices`、`security_opt`、`ipc`、`pid`、`uts`、`cgroup`、`runtime`、`shm_size`、`tmpfs`、`device_cgroup_rules` 不映射；`configs` / `secrets` 当前显式拒绝，不能部署

Docker Compose 部署会将服务级 `services.<svc>.gpus` 以及 `deploy.resources.reservations.devices` 映射为 Docker `HostConfig.DeviceRequests`，并保留 `options`；未写 `capabilities` 时默认 `[gpu]`。GPU 场景可使用：

```yaml
services:
  worker:
    image: nvidia/cuda:12.4.1-base-ubuntu22.04
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
```

当 `compose.yml` 不存在、需要从运行态反推生成时，bind mount 的 `source` 会按该容器目录输出为相对路径（例如 `./data`）；只有路径不在容器目录内、或恰好等于容器目录本身时才保留宿主机绝对路径。命名卷输出卷名，不输出 Docker 内部挂载目录，`--device` 会反推到 Compose `devices`，GPU 设备请求会反推到 `deploy.resources.reservations.devices` 并保留 `options`。反推会尽量与镜像 Dockerfile 默认配置做差分，避免把镜像内已有的 `CMD`、`ENTRYPOINT`、`ENV`、`EXPOSE`、`LABEL`、`STOPSIGNAL`、`USER`、`WORKDIR` 重复写入 compose。`ports` 未指定 `published` 时会保持 Docker 随机宿主端口发布语义，不会降级为仅 `expose`。

外部 Compose 项目接管说明：

- 同一 `com.docker.compose.project` 下的多个容器会合并为一个多服务 compose
- 反推内容会保留真实容器名为 `container_name`，便于后续重部署删除旧容器并保持名称稳定
- 重部署成功后会将 compose 写入 `docker.containerRoot/<PROJECT>/compose.yml`
- 暂不支持接管同一 `com.docker.compose.service` 下存在多个容器的 scaled 服务

### 重部署

执行前检查创建参数、名称冲突和旧容器状态。同名容器仅在项目标签匹配，或由请求明确指定且用它生成原始配置时，才纳入重建。预检失败时保留运行中的项目。

点击重部署窗口的「预览」后，先读取服务级变更清单，再次确认才真正更新。预览接口为 `POST /api/compose/docker/<NAME>/preview`，使用与重部署相同的 JSON 请求体，仅解析配置，不写文件或拉取镜像。Docker 对已有服务显示 `recreate`（仍将重建），并用 `configChanged` 标出配置是否发生变化；`create` 和 `remove` 分别代表新增与移除。预览基于当前配置，不保证运行态无漂移、端口可用或应用健康。预览权限与对应的 `PUT /api/compose/docker/:name` 一致。

```bash
isrvd_put "/compose/docker/<NAME>" "$(jq -n --arg content "$(cat docker-compose.yml)" '{content:$content}')"
```

`<NAME>` 可以是项目名，也可以是该项目下任意一个容器名；后端会通过 `com.docker.compose.project` 解析到项目名后整体重建关联容器。

重部署时同时更新 `.env`：

```bash
isrvd_put "/compose/docker/<NAME>" "$(jq -n --arg content "$(cat docker-compose.yml)" --arg envContent "$(cat .env)" '{content:$content,envContent:$envContent}')"
```

仅更新 `.env` 后重建（`content` 省略，沿用现有 compose.yml）：

```bash
isrvd_put "/compose/docker/<NAME>" "$(jq -n --arg envContent "$(cat .env)" '{envContent:$envContent}')"
```

清空 `.env`（提交空字符串）：

空字符串在解析和预检阶段也会忽略磁盘旧 `.env` 中的变量，确保变更预览、预检和实际部署使用一致的插值环境。

```bash
isrvd_put "/compose/docker/<NAME>" "$(jq -n --arg content "$(cat docker-compose.yml)" '{content:$content,envContent:""}')"
```

### 按服务更新镜像并重建

```bash
isrvd_put "/compose/docker/<NAME>" '{"serviceName":"<SERVICE_NAME>","image":"<NEW_IMAGE>"}'
```

## Swarm Compose

Swarm Compose 创建或更新服务时由 manager 查询仓库中的镜像摘要，运行任务的节点按需下载镜像层。镜像摘要查询失败时，Docker 可能继续使用原镜像引用。节点上的拉取错误可在 Swarm 任务状态中查看。私有仓库沿用现有的认证规则。[Swarm 服务 API](swarm/services.md)

Swarm 服务详情中的「更新状态」直接展示 Docker Engine 返回的更新状态与说明，使用页面已有的「刷新」获取最新结果。服务运行任务数与应用健康状态不能等同，更新请求成功只代表 Docker Engine 接收了操作。

Swarm 重部署窗口也会先使用 `POST /api/compose/swarm/<NAME>/preview` 只读预览，按服务显示 `create`、`update`、`unchanged`、`remove`。该清单只比较 Compose 规范生成的服务配置，不代表当前 Swarm 任务实际健康；未变化的配置也可能与运行态发生漂移。预览权限与对应重部署 PUT 接口一致。

### 部署策略与网络别名

以下字段在创建服务时下发到 Docker ServiceSpec，并在运行态反推 Compose 时保留，供再次编辑、保存或重部署：

| Compose 字段 | Docker ServiceSpec 字段 | 空值、零值与默认值 |
|---|---|---|
| `services.<svc>.networks.<network>.aliases` | `TaskTemplate.Networks[].Aliases` | 未填写或 `[]` 表示不配置额外别名；网络简写或空网络配置仍可使用 |
| `deploy.restart_policy.condition` | `TaskTemplate.RestartPolicy.Condition` | 支持 `none`、`on-failure`、`any`；未填写由 Docker 默认使用 `any` |
| `deploy.restart_policy.delay` | `TaskTemplate.RestartPolicy.Delay` | 未填写保留 Docker 默认延迟；显式 `0s` 表示立即重试，与未填写不同 |
| `deploy.restart_policy.max_attempts` | `TaskTemplate.RestartPolicy.MaxAttempts` | 未填写或 `0` 表示不限制重试次数；显式零值在回读 YAML 中保留 |
| `deploy.restart_policy.window` | `TaskTemplate.RestartPolicy.Window` | 按时长传递；显式 `0s` 保留，表示不限制重试计数窗口 |
| `deploy.update_config.parallelism` / `deploy.rollback_config.parallelism` | `UpdateConfig.Parallelism` / `RollbackConfig.Parallelism` | 策略存在但未填写该字段时使用 `1`；显式 `0` 表示全部并行，回读、保存后仍为 `0` |
| `deploy.update_config.delay` / `deploy.rollback_config.delay` | `UpdateConfig.Delay` / `RollbackConfig.Delay` | 未填写或 `0s` 表示批次之间不等待 |
| `deploy.update_config.failure_action` / `deploy.rollback_config.failure_action` | `UpdateConfig.FailureAction` / `RollbackConfig.FailureAction` | 更新支持 `pause` / `continue` / `rollback`；回滚支持 `pause` / `continue`；默认 `pause` |
| `deploy.update_config.monitor` / `deploy.rollback_config.monitor` | `UpdateConfig.Monitor` / `RollbackConfig.Monitor` | 非零时长原样传递；Docker Engine 对未填写和 `0s` 都使用默认监测窗口（当前为 `5s`），不能用 `0s` 关闭监测 |
| `deploy.update_config.max_failure_ratio` / `deploy.rollback_config.max_failure_ratio` | `UpdateConfig.MaxFailureRatio` / `RollbackConfig.MaxFailureRatio` | 未填写或 `0` 表示不容忍失败；非零比例原样传递 |
| `deploy.update_config.order` / `deploy.rollback_config.order` | `UpdateConfig.Order` / `RollbackConfig.Order` | 支持 `stop-first` / `start-first`，默认 `stop-first` |

整段策略未填写时不创建对应 ServiceSpec 对象，交由 Docker 使用默认策略；`{}` 表示使用该策略的默认值。当前 Compose 解析器不接受这三段策略的显式 `null`，需要使用 `{}` 或删除该字段。运行态读取包含 Docker 补齐后的默认值，因此 YAML 文本可能与输入不同；重新保存保留的是已支持转换的生效策略，未支持转换的字段不能保证保留。时长字段支持 `ms`、`s`、`m` 等单位。

例如 `stack.yml`：

```yaml
name: policy-demo
services:
  api:
    image: nginx:alpine
    networks:
      backend:
        aliases: [api-internal]
    deploy:
      restart_policy:
        condition: on-failure
        delay: 0s
        max_attempts: 3
        window: 30s
      update_config:
        parallelism: 1
        delay: 2s
        failure_action: rollback
        monitor: 10s
        max_failure_ratio: 0.25
        order: start-first
      rollback_config:
        parallelism: 0
        delay: 0s
        failure_action: pause
        monitor: 10s
        max_failure_ratio: 0
        order: stop-first
networks:
  backend:
    driver: overlay
```

```bash
isrvd_post "/compose/swarm" "$(jq -n --arg content "$(cat stack.yml)" '{content:$content}')"
# 强制从 Docker 运行态读取整个项目，检查上述策略和别名。
isrvd_get "/compose/swarm/api?force=true"
```

重部署会使用 Docker ServiceUpdate 原地更新已有服务，保留服务 ID；新增服务会创建，旧 Compose 中删除且已确认归属的服务会移除。直接指定无项目标签的服务时，可以从该服务生成配置并重部署。Docker 异步执行滚动更新；接口成功只表示更新请求已接受，不代表任务健康。多服务更新不是原子操作，出现部分失败时尽力恢复，恢复失败会报告错误。已有服务更新使用读取时的 Docker 版本号提交，并使用内部 `io.isrvd.compose.update-token` 标签与 Docker 前一份 spec 确认本次写入；出现并发修改时不会把未经确认的服务自动回滚。Docker 删除服务没有条件版本接口，移除前会检查版本，但检查与删除之间仍存在并发窗口；网络中断导致创建或删除的最终结果不明确时，错误会提示检查运行态。

### 部署

Swarm Compose 部署用法与 Docker Compose 一致，同样支持 JSON 与 multipart form：

```bash
isrvd_post "/compose/swarm" "$(jq -n --arg content "$(cat stack.yml)" '{content:$content}')"
```

上传本地附加文件：

```bash
isrvd_upload "/compose/swarm" "initFile" "./init.zip" "content=$(cat stack.yml)"
```

使用远程附加文件：

```bash
isrvd_post "/compose/swarm" '{"content":"<COMPOSE_YAML>","initURL":"<HTTPS_ZIP_URL>"}'
```

### 读取 compose 文件

```bash
isrvd_get "/compose/swarm/<NAME>"
```

`<NAME>` 可以是项目名，也可以是项目中的服务名。通过服务的 `com.docker.compose.project` 标签定位项目后，优先读取 `docker.containerRoot/<PROJECT>/compose.yml`；文件不存在或使用 `force=true` 时，按 project 标签聚合同项目服务并从运行态反推 Compose。没有项目标签时只反推指定服务。反推不会与镜像默认配置做差分，不能还原注释、变量表达式及未映射字段；涉及 Swarm configs/secrets 的服务不会静默反推，必须使用原始 Compose 文件。历史记录与重部署同样接受项目名或服务名。

Swarm Compose 与 Docker Compose 共用容器目录 `docker.containerRoot/<PROJECT>`：相对 bind path 基于该目录解析；从运行态反推时也按此目录输出相对路径。Swarm 下 `ports` 未指定 `published` 时，发布端口等于 `target`（而非随机端口）。注意 Swarm 是分布式部署，落盘目录仅在主节点；非主节点上的相对 bind path 需各节点自行准备。Swarm Stack 暂不映射 Docker 单机 `--gpus` / `HostConfig.DeviceRequests` 语义；GPU 调度需通过 Docker Swarm generic resources 等集群级配置另行管理。

### 重部署

```bash
isrvd_put "/compose/swarm/<NAME>" "$(jq -n --arg content "$(cat stack.yml)" '{content:$content}')"
```

重部署时同时更新 `.env`：

```bash
isrvd_put "/compose/swarm/<NAME>" "$(jq -n --arg content "$(cat stack.yml)" --arg envContent "$(cat .env)" '{content:$content,envContent:$envContent}')"
```

仅更新 `.env` 后重建（`content` 省略，沿用现有 compose.yml）：

```bash
isrvd_put "/compose/swarm/<NAME>" "$(jq -n --arg envContent "$(cat .env)" '{envContent:$envContent}')"
```

清空 `.env`（提交空字符串）：

```bash
isrvd_put "/compose/swarm/<NAME>" "$(jq -n --arg content "$(cat stack.yml)" '{content:$content,envContent:""}')"
```

### 按服务更新镜像并重建

```bash
isrvd_put "/compose/swarm/<NAME>" '{"serviceName":"<SERVICE_NAME>","image":"<NEW_IMAGE>"}'
```
