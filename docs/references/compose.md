# Compose API

Compose 接口用于单机 Docker Compose 与 Swarm Stack 的部署、读取配置、重部署，以及按服务更新镜像并重建。Docker Compose 读取与重部署支持按 `com.docker.compose.project` 标签聚合外部 `docker compose up` 启动的既有项目。

Docker 不可用时 `/compose/*` 返回 `503`；未配置 `docker.containerRoot` 时部署、读取配置和历史接口返回 `500`「未配置容器数据根目录」。

## Webview 部署入口

侧边栏「Compose 部署」包含「单机部署」「Swarm 服务」「应用市场」子菜单，桌面和移动端共用导航：

- 单机部署：`/compose/deploy?target=docker`，需 Docker 能力有效且有 `POST /api/compose/docker` 权限。
- Swarm 服务：`/compose/deploy?target=swarm`，需 Swarm 管理节点能力有效且有 `POST /api/compose/swarm` 权限。
- 应用市场：`/compose/marketplace`，至少一种部署目标可用时显示；选择模板后优先进入单机部署，仅 Swarm 可用时进入 Swarm 服务。

部署入口同时要求 Compose 能力有效；两种目标均不可用时隐藏整个「Compose 部署」菜单，单个目标不可用时隐藏对应子菜单。无目标参数的旧部署链接优先选择可用的 Docker 目标，否则选择 Swarm。清空表单不改变当前部署目标。

## 字段说明

### 部署请求

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `content` | string | 是 | 完整 compose yaml 文本 |
| `envContent` | string | 否 | `.env` 内容（`KEY=VALUE`）；省略则保留附加文件解压出的 `.env`（不存在时兜底创建空 `.env`，避免 `env_file` 因缺文件报错），提交则以其为准写盘并合并进变量插值环境 |
| `initURL` | string | 否 | 附加运行文件 zip 下载地址 |
| `initFile` | file | 否 | 附加运行文件 zip（仅 multipart）；与 `initURL` 同时提交不会报错，此时只使用 `initFile`，`initURL` 被忽略 |
| `forcePull` | boolean | 否 | `true` 时强制拉取最新镜像（即使本地已存在），默认 `false`；**仅 JSON 请求生效**，multipart 表单中传入会被忽略 |

> Docker 与 Swarm Compose 部署都支持 `initURL` / `initFile`；解压目标为 `docker.containerRoot/<NAME>/`。Swarm 场景下建议 `containerRoot` 指向各节点共享的存储（如 NFS），以便所有节点都能访问解压出的文件。

`.env` 提交约定：省略 `envContent` 保留附加文件或现有 `.env`；提交精确内容则覆盖；提交空字符串则清空。

部署前先做不读取 `env_file` 的结构预检并从中取得项目名（已插值并按 compose-go 规则规范化为小写）；完全未声明 `name` 时用 compose 内容短哈希兜底；若声明了 `name` 但其插值变量未提供，部署直接报错而不会退回哈希。

部署前的冲突校验（任一命中即报错）：

- 安装目录已存在 compose 配置：`目录 <DIR> 已包含 compose 配置，请先移除`
- Docker：同名容器已存在：`容器 <NAME> 已存在，请使用重部署接口`
- Swarm：同名服务已存在：`服务 <NAME> 已存在，请先移除`
- compose 中未定义任何服务：`compose 文件中没有定义服务`

部署失败时：若安装目录为本次新建则整体删除；若目录原本存在，则仅删除 compose.yml 并恢复原 `.env`。

状态码：`400` 为 JSON/表单解析失败、`content` 为空、请求体超过 `server.maxUploadSize`、路径参数 `:name` 非法；其余错误（含项目名非法、冲突校验、重部署参数校验、部署忙碌）返回 `500`。

### 重部署请求

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `content` | string | 按需 | 完整 compose yaml 文本；省略表示沿用现有 compose.yml，提交空字符串会被拒绝 |
| `envContent` | string | 按需 | `.env` 内容（`KEY=VALUE`）；省略表示保留现有 `.env`（不存在时兜底创建空 `.env`），提交空字符串表示清空，提交内容表示覆盖 |
| `serviceName` | string | 按需 | 要更新镜像的 compose 服务名（按服务更新） |
| `image` | string | 按需 | 新镜像名，`serviceName` 非空时必填 |
| `forcePull` | boolean | 否 | `true` 时强制拉取最新镜像，默认 `false` |

> 部分更新：未提交的字段保持不变；`content`、`envContent`、`serviceName` 至少提交一项；`serviceName` 与 `content`、`envContent` 互斥，`serviceName` 非空时 `image` 必填。

重部署前的配置保存在版本快照中。部署失败时，使用操作前读取的配置和 `.env` 状态回滚：先写回旧 compose 与 `.env`（含空文件或原本不存在的状态）并重建旧容器/服务，`.env` 恢复失败只记日志，不阻断实例回滚。错误响应的 `message` 附带回滚摘要，例如：`原错误；回滚：.env 回滚失败（…），容器回滚成功`（Swarm 为「服务回滚」）。正式加载和创建前先写入新 `.env`，确保 `env_file` 和变量插值使用新值。按服务更新镜像时，compose.yml 经 compose-go 加载后整体重新序列化（带 `# Auto-generated by iSrvd` 文件头）：原有注释与格式会丢失，`${VAR}` 会被替换为当时的实际值。

读取 Compose 配置时若落盘 `.env` 存在但读取失败（权限/IO），接口直接报错，不会把空串当作「无文件」。

### 部署记录与历史配置

每个 Docker/Swarm 项目最多保留最近 10 条记录（新到旧），同时按约 1 MiB 的加密记录预算移除最旧记录；单个快照的 JSON 明文不能超过 512 KiB。新建成功后记录 `deploy`；重部署在预检通过后先保存 `snapshot`（与最近记录配置一致时复用已有快照），再记录 `redeploy` 的成功或失败。预检失败和新建失败不记录。失败记录不包含配置快照或原始错误。记录只表示部署调用完成，不代表应用已通过健康验收；成功后快照读取失败或超限时仍保存无快照的成功记录。

```bash
isrvd_get "/compose/docker/<NAME>/history"
isrvd_get "/compose/swarm/<NAME>/history"
```

列表只返回以下只读字段，不返回配置内容：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 记录 ID |
| `time` | string | RFC3339 记录时间 |
| `action` | string | `snapshot`（变更前配置）、`deploy`、`redeploy` |
| `success` | boolean | 是否成功 |
| `hasSnapshot` | boolean | 是否可以读取配置快照 |

通过配置读取接口的 `revision` 参数获取快照，响应为配置详情；指定 `revision` 时优先于 `force`。读取快照沿用配置读取权限，记录列表需要相应 history 路由权限：

```bash
isrvd_get "/compose/docker/<NAME>?revision=<ID>"
isrvd_get "/compose/swarm/<NAME>?revision=<ID>"
```

API 恢复配置时，先读取快照，再通过重部署接口提交两个字段（空 `.env` 也必须显式提交）：

```bash
isrvd_put "/compose/docker/<NAME>" '{"content":"<HISTORICAL_COMPOSE_YAML>","envContent":"<HISTORICAL_ENV_OR_EMPTY>"}'
isrvd_put "/compose/swarm/<NAME>" '{"content":"<HISTORICAL_COMPOSE_YAML>","envContent":"<HISTORICAL_ENV_OR_EMPTY>"}'
```

存储与安全：

- 快照整体 AES-GCM 加密，密钥由 JWT 密钥派生，修改 JWT 密钥会导致此前的快照无法解密。
- 每份快照保存在 `docker.containerRoot/<PROJECT>/compose.<目标>-<记录ID>` 文件（含加密快照与元数据的 YAML，非可运行的 Compose 配置）；`.isrvd-history-docker.yml`、`.isrvd-history-swarm.yml` 仅保存轻量记录索引。即使系统配置使用 etcd，这些文件也写入项目本地目录（Swarm 为管理节点或共享存储），备份时随项目目录一起备份。
- 项目目录、索引和版本文件不能为符号链接；写入使用原子替换，新文件权限 `0600`。
- 索引提交成功后清理被淘汰和未被引用的版本文件；索引提交失败则移除本次新建的版本文件。
- 单个版本文件缺失、损坏或记录不匹配时，该记录降级为无快照，读取该版本返回错误；索引自身读取失败返回错误。
- 索引缺失时，从系统配置存储中的 `compose-<目标与项目名的 SHA256>.yml` 导入旧记录（支持本地文件与 etcd）；导入或快照拆分失败返回错误。
- 重部署前读取当前配置并保存快照，任一步骤失败均在删除实例前返回错误；部署完成后的记录写入失败只记日志。同一 isrvd 实例同时只执行一个 Compose 部署，忙碌时新请求立即返回错误。

历史配置恢复只覆盖 Compose 文本和 `.env`（原先不存在的 `.env` 会变为空文件），不恢复数据库、数据卷、附加文件、外部 `env_file` 或进程环境；未固定 digest 的镜像 tag 不能保证还原旧镜像。

### 变量插值优先级

从低到高：磁盘 `.env` < 请求中显式提交的 `envContent`（同键时优先于磁盘 `.env`） < 进程环境（与 docker compose 一致）。

### 部署结果

| 字段 | 类型 | 说明 |
|---|---|---|
| `projectName` | string | 实际使用的项目名 |
| `items` | string[] | 创建或重建的容器/服务，格式 `<name> (<12 位短 ID>)` |
| `installDir` | string | 项目落盘目录（Docker Compose 与 Swarm 均返回） |

### 配置详情

| 字段 | 类型 | 说明 |
|---|---|---|
| `content` | string | compose.yml 文本 |
| `envContent` | string | `.env` 文本（`KEY=VALUE`）；无落盘文件或内容为空时不返回 |
| `projectName` | string | 实际解析到的项目名 |
| `fileModTime` | number | `docker.containerRoot/<PROJECT>/compose.yml` 修改时间（Unix 秒）；无落盘文件时不返回 |
| `source` | string | 内容来源：`file` 表示落盘文件，`runtime` 表示从运行态反推 |

## Docker Compose

### 部署

Docker Compose 部署支持 JSON；上传附加运行文件时使用 multipart form。

部署请求总大小受 `server.maxUploadSize` 限制。

仅提交 compose 内容：

```bash
isrvd_post "/compose/docker" "$(jq -n --arg content "$(cat docker-compose.yml)" '{content:$content}')"
```

上传本地附加文件：

```bash
isrvd_upload "/compose/docker" "initFile" "./init.zip" "content=$(cat docker-compose.yml)"
```

使用远程附加文件：

```bash
isrvd_post "/compose/docker" '{"content":"<COMPOSE_YAML>","initURL":"<HTTPS_ZIP_URL>"}'
```

> `initURL` 由后端直接发起 HTTP GET 下载（仅 `http/https` 可用），**当前未校验目标是否为本机/内网/链路本地地址，也不限制重定向**；请仅使用可信地址。

### 读取 compose 文件

```bash
isrvd_get "/compose/docker/<NAME>"
```

`<NAME>` 可以是 iSrvd 项目名，也可以是带 `com.docker.compose.project` 标签的容器名。读取顺序：

1. 优先读取 `docker.containerRoot/<PROJECT>/compose.yml`，响应中的 `fileModTime` 为该文件修改时间
2. 文件不存在时，按 `com.docker.compose.project=<PROJECT>` 聚合同项目容器并反推多服务 compose
3. 无 compose project 标签时，退回单容器 inspect 反推

强制从运行态反推（跳过已有 `compose.yml`，但仍返回已有文件的 `fileModTime`）：

```bash
isrvd_get "/compose/docker/<NAME>?force=true"
```

Docker Compose 中的相对 bind path 会基于容器目录 `docker.containerRoot/<PROJECT>` 解析，部署、全量重部署、按服务更新镜像和失败回滚保持一致。后端统一使用 compose-go loader 解析与标准化 YAML，再直接生成 Docker SDK `container.Config` / `container.HostConfig`（Docker）或 `swarm.ServiceSpec`（Swarm）原始结构，不经过 iSrvd 自定义中间 DTO。

- **Docker 支持字段**：`entrypoint`、`command`、`dns`、`dns_opt`、`dns_search`、`extra_hosts`、`tty`、`stdin_open`、`read_only`、`stop_signal`、`sysctls`、`device_cgroup_rules`、`devices`、`security_opt`、`group_add`、`ipc`、`pid`、`uts`、`cgroup`、`runtime`、`shm_size`、`tmpfs`、`ulimits`、`cap_add`、`cap_drop` 等；`deploy.resources` 仅支持 `limits.memory`、`limits.cpus`（`mem_limit` / `cpus` 兜底）与 `reservations.devices`，`reservations.memory` / `reservations.cpus` / `limits.pids` 会被忽略
- **Swarm 支持字段**：`environment`、`entrypoint` / `command`、`working_dir`、`user`、`hostname`、`extra_hosts`、`tty`、`stdin_open`、`read_only`、`stop_signal`、`sysctls`、`cap_add` / `cap_drop`、`dns` / `dns_opt` / `dns_search`、`deploy.mode` / `replicas`、`networks`、`ports`、`volumes`、`deploy.placement.constraints`、`deploy.resources`（`limits.memory` / `cpus` / `pids`，`reservations.memory` / `cpus`）；`devices`、`security_opt`、`group_add`、`ipc`、`pid`、`uts`、`cgroup`、`runtime`、`shm_size`、`tmpfs`、`ulimits`、`device_cgroup_rules` 不映射

Docker Compose 部署会将服务级 `services.<svc>.gpus` 以及 `deploy.resources.reservations.devices` 映射为 Docker `HostConfig.DeviceRequests`，并保留 `options`；未写 `capabilities` 时默认 `[gpu]`。GPU 场景可使用：

```yaml
services:
  worker:
    image: nvidia/cuda:12.4.1-base-ubuntu22.04
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
```

当 `compose.yml` 不存在、需要从运行态反推生成时，bind mount 的 `source` 会按该容器目录输出为相对路径（例如 `./data`）；只有路径不在容器目录内、或恰好等于容器目录本身时才保留宿主机绝对路径。命名卷输出卷名，不输出 Docker 内部挂载目录，`--device` 会反推到 Compose `devices`，GPU 设备请求会反推到 `deploy.resources.reservations.devices` 并保留 `options`。反推会尽量与镜像 Dockerfile 默认配置做差分，避免把镜像内已有的 `CMD`、`ENTRYPOINT`、`ENV`、`EXPOSE`、`LABEL`、`STOPSIGNAL`、`USER`、`WORKDIR` 重复写入 compose。`ports` 未指定 `published` 时会保持 Docker 随机宿主端口发布语义，不会降级为仅 `expose`。

外部 Compose 项目接管说明：

- 同一 `com.docker.compose.project` 下的多个容器会合并为一个多服务 compose
- 反推内容会保留真实容器名为 `container_name`，便于后续重部署删除旧容器并保持名称稳定
- 重部署成功后会将 compose 写入 `docker.containerRoot/<PROJECT>/compose.yml`
- 暂不支持接管同一 `com.docker.compose.service` 下存在多个容器的 scaled 服务

### 重部署

```bash
isrvd_put "/compose/docker/<NAME>" "$(jq -n --arg content "$(cat docker-compose.yml)" '{content:$content}')"
```

`<NAME>` 可以是项目名，也可以是该项目下任意一个容器名；后端会通过 `com.docker.compose.project` 解析到项目名后整体重建关联容器。

重部署时同时更新 `.env`：

```bash
isrvd_put "/compose/docker/<NAME>" "$(jq -n --arg content "$(cat docker-compose.yml)" --arg envContent "$(cat .env)" '{content:$content,envContent:$envContent}')"
```

仅更新 `.env` 后重建（`content` 省略，沿用现有 compose.yml）：

```bash
isrvd_put "/compose/docker/<NAME>" "$(jq -n --arg envContent "$(cat .env)" '{envContent:$envContent}')"
```

清空 `.env`（提交空字符串）：

```bash
isrvd_put "/compose/docker/<NAME>" "$(jq -n --arg content "$(cat docker-compose.yml)" '{content:$content,envContent:""}')"
```

### 按服务更新镜像并重建

```bash
isrvd_put "/compose/docker/<NAME>" '{"serviceName":"<SERVICE_NAME>","image":"<NEW_IMAGE>"}'
```

## Swarm Compose

### 部署

Swarm Compose 部署用法与 Docker Compose 一致，同样支持 JSON 与 multipart form：

```bash
isrvd_post "/compose/swarm" "$(jq -n --arg content "$(cat stack.yml)" '{content:$content}')"
```

上传本地附加文件：

```bash
isrvd_upload "/compose/swarm" "initFile" "./init.zip" "content=$(cat stack.yml)"
```

使用远程附加文件：

```bash
isrvd_post "/compose/swarm" '{"content":"<COMPOSE_YAML>","initURL":"<HTTPS_ZIP_URL>"}'
```

### 读取 compose 文件

```bash
isrvd_get "/compose/swarm/<NAME>"
```

优先读取 `docker.containerRoot/<NAME>/compose.yml`；文件不存在时，仅把名为 `<NAME>` 的**单个** Swarm 服务反推为单服务 compose（不按 project 标签聚合，也不与镜像默认配置做差分）。

Swarm Compose 与 Docker Compose 共用容器目录 `docker.containerRoot/<NAME>`：相对 bind path 基于该目录解析；从运行态反推时也按此目录输出相对路径。Swarm 下 `ports` 未指定 `published` 时，发布端口等于 `target`（而非随机端口）。注意 Swarm 是分布式部署，落盘目录仅在主节点；非主节点上的相对 bind path 需各节点自行准备。Swarm Stack 暂不映射 Docker 单机 `--gpus` / `HostConfig.DeviceRequests` 语义；GPU 调度需通过 Docker Swarm generic resources 等集群级配置另行管理。

### 重部署

```bash
isrvd_put "/compose/swarm/<NAME>" "$(jq -n --arg content "$(cat stack.yml)" '{content:$content}')"
```

重部署时同时更新 `.env`：

```bash
isrvd_put "/compose/swarm/<NAME>" "$(jq -n --arg content "$(cat stack.yml)" --arg envContent "$(cat .env)" '{content:$content,envContent:$envContent}')"
```

仅更新 `.env` 后重建（`content` 省略，沿用现有 compose.yml）：

```bash
isrvd_put "/compose/swarm/<NAME>" "$(jq -n --arg envContent "$(cat .env)" '{envContent:$envContent}')"
```

清空 `.env`（提交空字符串）：

```bash
isrvd_put "/compose/swarm/<NAME>" "$(jq -n --arg content "$(cat stack.yml)" '{content:$content,envContent:""}')"
```

### 按服务更新镜像并重建

```bash
isrvd_put "/compose/swarm/<NAME>" '{"serviceName":"<SERVICE_NAME>","image":"<NEW_IMAGE>"}'
```
